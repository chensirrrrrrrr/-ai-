> 本材料只写**代码里真实存在的东西**（路径、字段、判定都可在仓库里核对），

## 一、开场：我负责什么（30 秒定调）

> 「我负责的是**学生成绩管理**：老师/顾问录入历次考试成绩（雅思、托福、校内科目），
> 学生本人只能查自己的成绩，管理层做统计口径的聚合查询。
> 它上游接学生档案，下游供**申请进度看板**和**AI 助手的成绩问答**两个场景消费。」

**模块边界（讲清楚不越界）**

| 属于本模块 | 不属于本模块（谁负责） |
| --- | --- |
| 成绩录入 / 查询、成绩与学生的关联、成绩条数统计 | 学生档案本身（`student` 表与学员域接口） |
| 成绩对外查询的**数据边界**（学生只能看自己的） | 成绩如何影响录取判断（在研判规则 `services/rules.py`） |
| 成绩在 AI 助手里的两个工具入口 | 报告里的成绩聚合口径（`services/reports.py`） |

## 二、业务逻辑：谁在什么场景用它

| 角色 | 能做什么 | 代码位置 |
| --- | --- | --- |
| 老师 / 顾问（employee） | 录入任意学生成绩；按学生 / 科目查全量 | `POST /api/v1/scores`（`staff_only`）、`GET /api/v1/scores` |
| 学生（student） | **只能查自己的**，传 `student_id` 也不作数 | `list_scores()` 里强制 `student_id = principal.ref_id` |
| 管理层（manager/admin） | 同上 + 报告聚合 | 报告模块 |
| AI 助手（Dify 工具） | 两个入口，分工见 §四 | `services/agent_tools.py` |

**三个真实使用场景**（现场可讲）
1. 顾问录一次雅思成绩 → 学生档案的「成绩条数」计数 +1（`/students/{id}/progress` 里有 `score_records`）；
2. 学生问助手「我雅思多少」→ 走 `my_scores` 工具，只返回本人；
3. 管理层问「这个学生近几次考试」→ 走 `student_scores` 工具或后台列表。

## 三、接口设计（照着这张表讲，别背代码）

| 接口 | 方法 | 权限 | 关键行为 |
| --- | --- | --- | --- |
| `/api/v1/scores` | POST | `staff_only`（employee/manager/admin） | 先校验学生存在（不存在 → **404** 而不是 500）；写审计日志 `score.create`；`commit` 后返回 id |
| `/api/v1/scores` | GET | 登录即可（`get_principal`） | 可按 `student_id` / `subject` 过滤；**学生角色强制收敛为自己**；按考试日期倒序，`limit 100` |
| `/internal/tools/student_scores` | POST | 工具通道（min_role **employee**） | 早期只读接口，`student_id` **可选**，不传就跨学生返回（给顾问/管理层查库用） |
| `/internal/tools/my_scores` | POST | 工具通道（min_role **student**） | **`student_id` 必填**，只返回该学生；这是学生端「我的成绩」 |

**加分说法（两个工具为什么要分成两个）**
> 「同一个能力开两个工具，看着像是冗余，其实是**权限矩阵的必然结果**：
> `student_scores` 的 `student_id` 是可选的，门槛必须设成 employee —— 否则学生不传参就能拖全库成绩；
> 但这样一来学生调用它会被 403。所以另开 `my_scores`：必填 `student_id`、门槛降到 student。
> 两个工具的分工有专门的回归测试锁着，谁以后想『合并成一个』，测试会先拦下来。」

## 四、数据模型（`student_score` 表）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | BigInt PK | 分布式 id（本项目统一 BigInt 主键） |
| `student_id` | BigInt FK → `student.id`，**索引** | 关联学生；查询几乎都带它 |
| `exam_name` | String(64) | 考试名称（雅思 / 托福 / 期末…） |
| `subject` | String(32) | 科目 |
| `score` | **Numeric(6,2)** | 实际得分 |
| `full_score` | Numeric(6,2)，默认 100 | 满分（雅思满分 9、校内 100，所以满分必须可配） |
| `exam_date` | Date，**索引** | 考试日期（排序用，可空） |
| `created_at` | DateTime | 录入时间 |

**加分说法（两个为什么）**
- **为什么分数字段用 `Numeric(6,2)` 而不是 `float`？**
  成绩是要**比大小、求平均**的（报告里有 GPA/均分聚合），二进制浮点会有 `0.1+0.2` 那类误差，
  分数这种「差 0.01 就有争议」的数据必须用定点数；返回给前端时才 `float(row.score)` 转成 JSON 友好的数值。
- **为什么 `full_score` 可配而不是写死 100？**
  雅思满分 9、托福 120、校内科目 100 —— 写死就得靠「换算」这种容易错的补丁，不如存原始满分。

## 五、实现：分层与关键代码

**分层**（如实讲，别照搬「四层」的说法）

```
main.py（应用装配、中间件、异常兜底）
   └─ api/v1/*.py（路由：鉴权 → 取参 → 调 services → 包信封）
        └─ services/*.py（业务能力：与 HTTP 解耦，可被工具/定时任务复用）
             └─ models.py / db.py（数据模型与会话）
```

> 「我们**没有单独的 crud 层**：成绩这种简单写操作在 API 层直接操作 Session，
> 跨接口复用的业务能力才下沉到 services（比如成绩相关的工具入口、报告聚合）。
> 多一层 crud 只会让『这个逻辑到底在哪』变成猜谜。」

**录入（`create_score`）三步**：校验学生存在 → `db.add` + `flush` → 审计留痕 → `commit`。

```python
if db.get(Student, body.student_id) is None:
    raise NotFound(f"学生 {body.student_id} 不存在")
row = StudentScore(**body.model_dump())
db.add(row); db.flush()
audit.record(db, action="score.create", actor_id=principal.subject, ...)
db.commit()
```

**查询（`list_scores`）的两道口径**

```python
if principal.role == "student":
    student_id = principal.ref_id      # 学生的入参不作数，一律收敛为自己
query = db.query(StudentScore)
if student_id: query = query.filter(StudentScore.student_id == student_id)
if subject:    query = query.filter(StudentScore.subject == subject)
rows = query.order_by(StudentScore.exam_date.desc()).limit(100).all()
```

> 加分说法：「学生角色的 `student_id` 入参我**直接覆盖**而不是校验报错 ——
> 报错等于告诉对方『你传的 ID 存在但我就是不给你』，覆盖则只暴露『你自己的』，
> 顺带把『遍历 ID 探测成绩存不存在』这条路也堵了。这和对话接口里 `role` 一律取 Token 是同一套思路。」

## 八、高频提问与应答

**Q1：为什么不给学生开放录入？**
录入是**写入**，必须走 staff 权限；学生端只有查询，且强制收敛为自己。写操作还额外做了审计留痕（`score.create`），谁在什么时候录的都能追溯。

**Q2：学生传别人的 `student_id` 会怎样？**
不会报错，会被**服务端覆盖成自己的 ref_id** —— 返回结果只含自己的成绩。这样既不泄露「这个 ID 成绩存不存在」，又堵掉了遍历探测。

**Q3：分数字段为什么不是 float？**
`Numeric(6,2)` 定点数。成绩要参与平均与比较，浮点误差会在边界值上产生争议（比如 6.0 显示成 5.999999）。只在返回给前端时转 `float`。

**Q4：两个成绩工具是不是重复？**
不是。见 §三：`student_scores`（employee，`student_id` 可选）是查库用的，`my_scores`（student，必填）是学生端入口，权限矩阵要求它们必须分开，且有测试锁住分工。

**Q5：成绩能改能删吗？**
当前版本**只做录入与查询**（需求范围如此）。如果将来要加，改/删必须像写操作一样带审计，并且沿用同一套权限判定 —— 这是设计上预留的扩展点，不是遗漏。

**Q6：一次查多少条？会不会慢？**
`limit 100` + `exam_date` 倒序，`student_id` 有索引。压测：并发 50 时成绩查询 **p95 ≈ 160 ms、0 错误**，吞吐约 500 req/s。

**Q7：成绩和申请进度怎么联动？**
学生档案接口返回 `score_records`（成绩条数），申请进度看板展示阶段时间线；成绩本身不参与录取判定，判定在研判规则里。

**Q8：AI 助手查成绩会泄露吗？**
工具侧两道门：HMAC 签名（或静态 Key）+ 工具级 `min_role`；`my_scores` 还要求必填 `student_id`。另外客户侧（不是成绩侧）的 `lead_query` 也做了**行级收敛** —— employee 只查自己名下的客户。

**Q9：这个模块你做的最有价值的设计是什么？**
（推荐答）**学生端入参一律覆盖 + 两个工具按权限矩阵拆分**。前者把「越权」和「探测」一起堵了，后者把「能力复用」和「最小权限」的矛盾解开了，而且都用测试固定住，不会被后人顺手改回去。

**Q10：如果让你重做一次，会改什么？**
两点：① 成绩聚合（平均分、趋势）目前散在报告模块，应该单独抽一个 `services/score_stats.py` 让口径唯一；
② 录入目前是单条，批量导入（Excel）可以复用已有的材料解析能力。
