## 二、代码是否有冗余？—— 有，均可安全清理

### 2.1 死代码：20 个 schema 类全仓未被引用 🔴 主要项 ✅ 已删除

- `app/schemas.py` 共 **51** 个类 → 删 20 后剩 **31** 个。
- 根因：全项目 **`response_model=` 使用 0 次** —— 响应统一走自研信封 `{code,message,data}`，接口层未声明响应模型，于是这批 `*Out` 契约类成了孤儿。
- ⚠️ **判定口径要修正一次**：第一版扫描把「只被 `schemas.py` 内部引用」的类也当成了死代码，得出 **24** 个。
  改用**传递可达性**（roots = 外部引用；再沿内部引用闭包扩散）复核后，真死是 **20** 个 ——
  `RuleItem` / `RuleProduct`（`RuleImportRequest.products` ↔ `RuleProduct.rules`）、
  `DeadlineItem` / `ProgressItem`（`DeadlineImport.items` / `ProgressImport.items`）**都是活的，不能删**。

```
ORMBase, TokenResponse, ReferenceItem, ChatResponse, AsrResponse, LeadOut, FollowupOut,
ScreeningOut, StudentOut, ScoreOut, RequestOut, TicketOut, AlertOut, ActivityOut,
EnrollmentOut, ReportOut, DailyReportOut, Nl2SqlResponse, AuditLogOut, KbDocumentOut
```

> 附带影响：响应结构无 schema 校验（无 FastAPI 自动响应序列化/过滤）。**清理前建议先确认是否有意保留为「对外契约文档」**，否则删。
> **决策**：这 20 个类无任何引用方（不是文档、也不是契约 —— 真契约在 docx 接口表里），且与 §2.1 根因同源，
> 故**整体删除**；同时移除因此失效的 `ConfigDict` 导入。删除后 31 个类仍覆盖全部请求体契约。

## 九、限流 + 监控探针（2026-09-17 同日第 5 项加固）

盘点清单里的第 ⑤ 项：工程侧两块「线上才会痛」的能力 —— **接口限流**（此前 0 命中，登录可被无限爆破、
LLM 对话可被无限刷）与**运行时监控**（看不到 QPS / 错误率 / p95 / 意图命中情况）。

### 9.1 限流（`app/services/ratelimit.py`，纯标准库）

- **实现**：进程内滑动窗口（60 行标准库），不引 slowapi / redis —— 单进程部署下与
  slowapi 的内存后端语义等价；多 worker / 多机时换 Redis 计数，`enforce()` 接口不变。
- **两道闸**：
  | 接口 | 维度 | 默认阈值（`RATE_LIMIT_*_PER_MIN`） | 位置 |
  | --- | --- | --- | --- |
  | `POST /auth/token` | 每 IP | 30/min（防爆破） | 密码校验**之前**，爆破者拿不到「用户名是否存在」的信息 |
  | `POST /chat/message` + `/chat/stream` | 每账号 | 120/min（防刷 LLM） | 意图路由之前，被限的请求**一次模型调用都不花**；流式与普通消息同一桶，防绕行 |
- **响应**：429 + 信封 `code=42900` + `data.retry_after`（建议等待秒数）；超限窗口滑出即自动恢复；
  `RATE_LIMIT_ENABLED=false` 一键关闭。

### 9.2 监控探针（`app/services/metrics.py`，随 `/api/v1/health` 暴露）

`GET /health` 的响应新增 `metrics` 字段（进程内存活，重启清零）：

| 块 | 内容 |
| --- | --- |
| `requests` | 总量 / 4xx+5xx 错误数 / p50 / p95（中间件逐请求记账，路径数字段折叠成 `:id` 防 key 膨胀） |
| `chat` | 总数、dispatch / clarify / fallback 分布与占比、**dispatch_rate（意图可执行率，准确率的代理指标）**、平均置信度、对话 p50/p95、路由来源（prefilter/dify/fallback）、Top5 意图 |
| `rate_limit` | 开关、阈值、拒绝总数与分布 |

> 口径注意：`/health` 自身这次请求是「先算快照、后记账」（中间件在响应后计数），
> 快照里的 `requests.total` 不含本次 —— 测试里已把这个口径钉住并写明。

### 9.3 测试与回归

新增 `tests/test_rate_limit_metrics.py`（**9 条**）：滑动窗口三相位（阈值内放行 / 超限拒绝带
retry_after / 滑出恢复）、`enforce` 抛 429（含 code 与 data）、登录爆破拦截 + 换 IP 不误伤、

## 十、敏感字段加密 + 内容安全（2026-09-17 同日第 6 项加固）

盘点清单第 ⑥ 项，也是最后一项：**客户手机号明文落库**（`id_card_masked` 只是命名约定）与
**用户消息原样进大模型/审计**（PII 无脱敏、无违禁拦截）。

### 10.1 字段级加密（`app/services/crypto.py`，默认关闭，`FIELD_ENCRYPTION_KEY` 开启）

手机号同时有三种互相冲突的诉求，用「三件套」一次解决：

| 列 | 存什么 | 解决什么 |
| --- | --- | --- |
| `phone` | **打码值** `138****5678` | 展示 / API 输出 —— 结构不变，前端零改动 |
| `phone_enc` | **Fernet 密文**（可解回全号） | 存储安全 —— 拖库/备份泄露不再等于 PII 泄露 |
| `phone_hash` | **HMAC-SHA256**（确定性） | 查重 / 等值检索 —— Fernet 带随机 nonce 无法等值匹配，必须单独一列 |

- **开启后行为**：新建客户的明文手机号不落库；接口输出打码值；审计 detail 只记打码值；
  查重、`lead_query` 工具按号检索走 HMAC（纯数字关键字 ≥7 位也走 HMAC 兜底）；
  查重条件 `or_(HMAC, 明文全号)` 兼容「密文行 + 历史明文行」**并存过渡期**。
- **关闭时**：`apply_phone` 退化为 `(明文, None, None)` —— 与历史行为逐字节一致，512 条旧用例零改动全绿。
- **存量迁移**：新列可空 ⇒ 启动时由 `_sync_missing_columns` 自动补列（只加不改）；
  明文回填用 `python scripts/encrypt_backfill.py`（幂等、跳过已打码行、支持 `--dry-run`），
  ⚠️ 跑之前先备份数据库 —— key 丢失即不可恢复。

### 10.2 内容安全（`app/services/content_safety.py`，默认开启）

`POST /chat/message` 在限流之后、意图路由之前先过 `screen()`：

| 结果 | 处理 |
| --- | --- |

> 本模块是「没有外部服务时也有兜底」，接口留好。
> 范围说明：打码只作用于**对话入口**；材料研判的正文是业务输入（姓名/GPA 等）不在此列。

## 十一、Dify 工具 `lead_query` 行级收敛（2026-09-17 第 7 项，方案 A）

§八 给 HTTP 侧做了行级隔离后，工具链路还留着一条「合法凭据 + 全库可见」的通道：
`lead_query`（含旧别名 `lead_lookup`）对 employee 角色可按关键字/手机号/状态查全库客户。
经确认后按**方案 A** 收敛，两条入口口径彻底一致。

### 11.1 规则

| 调用方 | 可见范围 | 说明 |
| --- | --- | --- |
| manager / admin | 全量 | 不依赖 `actor` |
| employee | **自己名下**（`owner_id` 强制收敛） | 显式传别人的 `owner` 也翻不出去 |
| employee 但**身份不可确认** | 空结果 + `hint`（fail closed） | `actor` 不是有效登录账号名（如默认的 `dify`）、账号停用、非员工账号 |

身份解析：`_operator_employee_id()` 用 `actor_subject`（= `sys_account.username`）查账号，
要求**在职 + 员工类角色 + 有 ref_id**；返回里带 `scope`（`all` / `own` / `unknown_operator`）。

> ⚠️ **部署配套（必须做）**：工具通道默认 `actor="dify"`，员工角色查询会直接拿到空结果。
> Dify 侧调用 `/internal/tools/*` 时**必须带上操作人的登录账号名**（请求体 `actor`），
> 与 `_dify_inputs` 注入 `role` / `student_id` 是同一类要求 —— 不带就查不到，是刻意设计。

### 11.2 测试

带 `teacher` → 空；manager → 全量），静态 Key 通道两个用例同步带 `actor`。

**回归**：pytest **533 passed / 93%**（`agent_tools.py` 仍 **100%**）+
