## 二、代码是否有冗余？—— 有，均可安全清理

### 2.1 死代码：20 个 schema 类全仓未被引用 🔴 主要项 ✅ 已删除

- `app/schemas.py` 共 **51** 个类 → 删 20 后剩 **31** 个。
- 根因：全项目 **`response_model=` 使用 0 次** —— 响应统一走自研信封 `{code,message,data}`，接口层未声明响应模型，于是这批 `*Out` 契约类成了孤儿。
- ⚠️ **判定口径要修正一次**：第一版扫描把「只被 `schemas.py` 内部引用」的类也当成了死代码，得出 **24** 个。
  改用**传递可达性**（roots = 外部引用；再沿内部引用闭包扩散）复核后，真死是 **20** 个 ——
  `RuleItem` / `RuleProduct`（`RuleImportRequest.products` ↔ `RuleProduct.rules`）、
  `DeadlineItem` / `ProgressItem`（`DeadlineImport.items` / `ProgressImport.items`）**都是活的，不能删**。

```
ORMBase, TokenResponse, ReferenceItem, ChatResponse, AsrResponse, LeadOut, FollowupOut,
ScreeningOut, StudentOut, ScoreOut, RequestOut, TicketOut, AlertOut, ActivityOut,
EnrollmentOut, ReportOut, DailyReportOut, Nl2SqlResponse, AuditLogOut, KbDocumentOut
```

> 附带影响：响应结构无 schema 校验（无 FastAPI 自动响应序列化/过滤）。**清理前建议先确认是否有意保留为「对外契约文档」**，否则删。
> **决策**：这 20 个类无任何引用方（不是文档、也不是契约 —— 真契约在 docx 接口表里），且与 §2.1 根因同源，
> 故**整体删除**；同时移除因此失效的 `ConfigDict` 导入。删除后 31 个类仍覆盖全部请求体契约。

### 7.1 收口过程中发现并已修复的一处不一致

`_screening_batch` 的文档承诺是「每条都会单独落库，**单条失败不影响其余**」，原实现里
`items` 的失败被 `try/except` 兜住了，但 **`lead_ids` 拼客户文本（`_lead_text`）发生在 try 之外** ——
只要 `lead_ids` 里有一个客户不存在，**整批直接抛错**，与承诺不符。

**已修复（同日，经确认后执行）**：`_lead_text` 的调用改为逐条容错 —— 客户不存在只记该条
`ok=False`（序号与提交顺序一致），其余照常执行；`total` 改为按实际处理条数计。
同时把「`lead_ids` 里混入坏 ID 不炸整批」写进
`test_screening_batch_guards_and_partial_failure`（断言 2 成功 / 2 失败、序号 0–3 与提交顺序对应）。

> 这是本轮**唯一**一处 `app/` 代码改动，属行为变更但只放宽失败隔离、不影响成功路径的返回结构；
> 修复后全量回归重跑：pytest **502 passed / 93%** + 起服体检 / HTTP 冒烟 / 浏览器 E2E **23 项全过**。
