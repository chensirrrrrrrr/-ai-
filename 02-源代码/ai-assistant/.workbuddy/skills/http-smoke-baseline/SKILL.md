# HTTP 冒烟基线

## 一、为什么不能只用 pytest

`pytest` + `TestClient` 是**进程内**调用：不经过真实网络、不经过真实端口、
不经过静态服务器、不读启动脚本设的环境变量。所以下面这些它一律抓不到：

| 只有真起服务才暴露的问题 | 例子 |
|---|---|
| 启动脚本 / 端口占用 / 端口避让 | 双击 `start.bat` 后其实起在了别的端口 |
| CORS 白名单 | 前端跨域被拦，但进程内测试不校验 Origin |
| 静态资源可加载性 | `index.html` 引了一个 404 的 js/css |
| 环境变量注入 | `.env` 里的值没被读到，跑的是代码默认值 |
| 真实启动失败 | import 期报错、依赖缺失、迁移没跑 |

所以两套都要有：**pytest 保证逻辑，冒烟保证"真的跑起来了"**。

## 二、脚本骨架

见 `scripts/smoke_test_template.py`。核心是一个 `check()` 助手：

```python
def check(client, name, method, path, *, expect=200, expect_code=0, **kwargs):
    """期望 HTTP 状态 + 业务 code 双校验；异常兜底成一条 FAIL 而不是崩掉整个脚本。"""
```

四个设计要点，缺一个都会让冒烟变得不好用：

### 1. HTTP 状态码 **和** 业务 code 都要校验

统一响应信封通常是 `{"code": 0, "message": ..., "data": ..., "trace_id": ...}`。
只断言 `status == 200` 会漏掉"HTTP 200 但业务失败（`code` 非 0）"这一大类问题。
两个都断言，detail 里把两者都打出来：

```
detail = f"HTTP {resp.status_code} code={code}"
```

**例外**：非统一信封的端点（`/docs`、`/openapi.json`、静态资源、健康探针的某些实现）
用 `expect_code=None` 跳过业务码校验，否则会写一堆为了绕过校验的丑陋特例。

```python
check(client, "OpenAPI 文档", "GET", "/openapi.json", expect_code=None)
```

### 2. 异常必须被兜住，不能中断整轮

网络不通、JSON 解析失败、超时——都要变成**一条 FAIL 记录**并继续跑，
否则脚本会在第一个红点上崩掉，你只看得到第 1 个问题。
`try/except Exception` 包住整个请求，并记下 `EXCEPTION <message>`。

### 3. 每条用例记耗时

`time.perf_counter()` 夹住请求，落进结果元组。价值在于：
**报告里能一眼看出"哪个接口突然变慢"**——冒烟报告是少数会顺手给出性能回归信号的产物。

### 4. 退出码 = 有失败就非 0

`return 0 if failed == 0 else 1`。这样它能被 CI 和一键启动器直接调用。

## 三、用例覆盖顺序（照着抄）

按「先能连上，再谈业务」的顺序，前面的失败会让后面的自然失败，排查路径清晰：

1. **存活 / 就绪**：`/health`、`/ready`（就绪探针要区分"进程活着"与"依赖可用"）
2. **规范文档**：`/openapi.json`（顺便证明 app 装配完成，用 `expect_code=None`）
3. **各角色登录**：至少 admin / manager / 普通员工 / 受限角色 各拿一个 token
   （只测 admin 会漏掉权限串味的问题）
4. **鉴权边界**：
   - 无 token 访问受保护端点 → 期望 **401**
   - 低权限 token 访问高权限端点 → 期望 **403**
   - 拿越权 token 去改数据 → 期望 **403** 且数据未变
5. **各业务链路主路径**：列表 → 详情 → 创建 → 修改 → 收尾操作
6. **参数校验**：故意发坏请求体 → 期望 **422**（证明校验中间件真的在跑）
7. **幂等性**：同一个 `Idempotency-Key` 发两次 → 第二次应返回同一条记录而不是新建
8. **写后读一致性**：刚创建的记录能立刻被列表/详情查到
9. **善后**：把冒烟产生的数据清掉，或用固定前缀命名便于识别
   （反复跑冒烟不该让演示数据膨胀）

**造数要带 uuid**：`name=f"冒烟测试客户-{uuid.uuid4().hex[:8]}"`。
用固定名字反复跑会撞唯一约束，或者更糟——默默改到了别人的数据。

## 四、产出一份 markdown 报告

写在 `reports/smoke_report.md`：目标地址、执行时间、总数/通过/失败、累计耗时，
然后一张逐条表格（序号 / 用例 / 结果 / 耗时 / 说明），最后一行结论。
用 ✅ / ❌ 让它在编辑器里一眼能扫。

报告比终端输出重要，因为终端滚完就没了，而报告可以贴进交付文档、
也可以作为"这次改动没有破坏既有链路"的证据留档。

## 五、挂到一键启动器上

冒烟脚本真正的价值是在**每次启动时就发现"起不来/起错了"**。
在 `--selfcheck`（起服 → 体检 → 收服）里串上它：

```
>>> 接口检查          # 十几条轻量 HTTP 探针（探活、鉴权链路、前端资源）
>>> 冒烟测试          # 调用 scripts/smoke_test.py，产出报告
>>> 收服
```

分层的好处：**接口检查失败 → 立刻停，别浪费 30 秒跑冒烟**；
接口检查通过但冒烟红 → 说明服务活着但业务链路有问题，指向明确。

注意冒烟需要**独占端口**：自检模式进场就要先探测端口有没有被本项目占用，
占用了就明确报错退出，而不是硬起在别的端口上跑一份"假的通过"。
