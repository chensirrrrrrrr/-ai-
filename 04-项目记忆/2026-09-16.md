## 排查：「有两个后台任务还在运行，为什么没结束」（17:00 左右）

**结论：不是卡死，是本来就该长跑的开发服务器 + 一个我没主动停的老 shell。**
一个是 uvicorn（设计上就不会自己退出），另一个是 14:56 那次跑完用例后没退出的残留 bash。
两个都无害，且都不该停 —— 8000 上跑着的是当前唯一的 live 服务。

### 完整进程血缘（`Get-CimInstance Win32_Process`）
```
node.exe 10572 (openclaw gateway:18789)   ← 第三方，10:35 起，全程无关
node.exe 5984  (weixin-acp)               ← 第三方，10:35 起，无关

bash 39564 (14:56:39)                     ← 【任务A】14:56 那批 shell 的根
 └ bash 19036 (14:56:40)
    └ bash 35836 (14:56:40)               ← 最内层，用例跑完就没再退

bash 28880 (16:04:55)                     ← 【任务B】本次起服务的那个 run_in_background
 └ bash 42928 (16:04:55)
    └ bash 10316 (16:04:55)
       └ python 34668 (16:04:55) uvicorn  ← 父
          └ python 39532 (16:04:56) uvicorn ← 子，持有 8000 的监听 socket
```

### 判定依据
- `34668` 与 `39532` 是**父子对**（parent 分别是 10316 / 34668），不是两个独立服务。
  Windows 上 uvicorn 会 spawn 子进程，**监听 socket 归子进程** —— 这是正常形态，不是泄漏。
- 8000 端口 `Listen` 的 `OwningProcess=39532`，`/api/v1/health` 返回
  `HTTP 200 dify_mode=live dify_ready=True dify_key_count=7` → 服务健康。
- 11434（Ollama）`pid=39868` 单独一类，与上面无关。

### 判定手法沉淀（下次直接用）
- `Get-CimInstance Win32_Process -Filter "Name='bash.exe' or Name='python.exe'"`
  看 `ParentProcessId` 串血缘 —— **一眼区分「长驻服务」和「跑完没退的 shell」**。
- `Get-NetTCPConnection -LocalPort <port> -State Listen` 拿 `OwningProcess`，
  确认到底哪个 PID 真正占着端口。
- 工具启动的后台命令，其进程树上的 bash 链**不会随命令结束而消失**，
  所以「后台任务还在运行」里很可能混着上一批 task 的 shell —— 先串血缘再下结论。

### ⚠️ 核心坑：launcher 的 `spawn_headless` 也逃不过沙箱进程树回收

- `--headless` 用的是 `DETACHED_PROCESS | CREATE_NO_WINDOW`，看着像能脱离，
  但 **bash 工具把整条命令放进 Windows Job Object，命令一结束就 `TerminateJobObject`**，
  detached 子进程照样被连坐杀掉。
- 实测：`launcher.py --headless --no-browser --smoke` 跑完 → **smoke 149/149 全过**，
  但紧接着 `--status` 报 **两个 [FAIL]**、8010/8020 **FREE**、pid 全 GONE，
  `backend.log` 正好停在 smoke 最后一条请求（17:23:54）。服务是被回收的，不是启动失败。
- **正解**：让「最外层命令不退出」把 job 撑住，并且用工具的 `run_in_background`：
  ```bash
  python scripts/launcher.py --headless --no-browser; exec sleep 31536000
  ```
  实测：`--status` 两个 [OK]、冒烟 **149/149**、服务常驻（backend pid=41596 / frontend pid=616）。
- 反面写法全部失败：`nohup ... &`、`start /b`、任何「跑完就返回」的组合。
- 代价：后台任务里留一个 `sleep` 进程；停服要 `launcher.py --stop` **加**停掉该后台任务。

## 调研：Dify 各应用能否改成「工作流模式」（只读，未改动任何配置）

用户问「能不能把 dify 的各个 agent 变成工作流模式，实现难度大吗」。查证结论如下。

### 现状（`docker-db-1` 的 `apps` 表，8 个应用，status=normal）
| mode | 应用 |
|---|---|
| chat | 客服 Agent / 学生助手 Agent / 企业助手 Agent / 心理关怀 Agent（+ 非交付范围的 `AI课程知识库助手`） |
| workflow | 路由分发 Agent / 筛选 Agent / 报告 Agent |

⚠️ **这 4 个业务应用名字虽然叫「Agent」，但 mode 是 `chat`（提示词型 Chatbot），不是 Dify 的 Agent 模式。**
判据：`app_model_configs.agent_mode` 最新一条是 `{"enabled": false, "strategy": "router", "tools": []}`
⇒ `App.is_agent` 为 False。这直接影响后面的转换结果，见下。

### 🔴 核心发现 1：Dify 官方有转换接口，且 chat 源转出来的是 **Chatflow**
`POST /console/api/apps/<app_id>/convert-to-workflow`
（controller：`/app/api/controllers/console/app/workflow.py:733`，装饰器限 `mode=[CHAT, COMPLETION]`）

关键一行（`/app/api/services/workflow/workflow_converter.py::WorkflowConverter.convert_to_workflow`）：
```python
new_app.mode = AppMode.ADVANCED_CHAT if app_model.mode == AppMode.CHAT else AppMode.WORKFLOW
```
⇒ **chat → `advanced-chat`（Chatflow，对话型工作流），不是非对话的 `workflow`。**

**这一点决定难度**：Chatflow 与 Chatbot 共用同一个端点 `POST /chat-messages`，
所以 `app/services/dify.py` 的 `chat()` / `stream_chat()`、以及前端 SSE **一行都不用改**。

### 🔴 核心发现 2：转换会把配置自动映射成节点
```
variables               -> start 节点
model_config            -> llm 节点
prompt_template         -> llm 节点（提示词搬过去）
file_upload             -> llm 节点
external_data_variables -> http-request 节点
dataset                 -> knowledge-retrieval 节点   ← 知识库变显式节点
show_retrieve_source    -> knowledge-retrieval 节点
```
chat 源额外补一个 **`answer` 节点**（答节点 = 对话式 Chatflow 的标志；workflow 源则是 `end` 节点）。
features 里 `retriever_resource` 被保留 ⇒ 引用回传开关跟着走。
⚠️ **生成的是新应用**（`new_app_id`），旧应用保留不删；且带的是 **draft** workflow。

### ⚠️ 一个陷阱（本次没踩，但要记住）
`_convert_to_app_config()` 里有一句副作用：`if mode == AGENT_CHAT or app.is_agent: app_model.mode = AppMode.AGENT_CHAT`。
而 `new_app.mode` 是**在这之后**用 `app_model.mode == AppMode.CHAT` 判断的 ——
**如果原应用 `is_agent=True`，转换结果会变成非对话的 `WORKFLOW`，而不是 Chatflow。**
本项目的 4 个应用 `agent_mode.enabled=false`，所以不受影响，转换会正确得到 Chatflow。

### 两条路线的难度对比
| | Chatflow（advanced-chat） | 非对话 Workflow |
|---|---|---|
| 端点 | `POST /chat-messages`（不变） | `POST /workflows/run` |
| 后端改动 | **零** | `chat.py` 两条路径重写 |
| 前端 SSE | 不变 | 事件类型全变（workflow_started / node_finished / workflow_finished） |
| 多轮对话 | 有 `conversation_id` | **没有**，要自己用 `conversation_variables` 维护 |
| 返回值 | `answer` + `metadata.retriever_resources` | `outputs`，references 结构不同 |
| 难度 | **低** | 高，且不适合客服/学生助手这类对话场景 |

### 转换后必须注意的点
1. **是新建应用** ⇒ 新 app_id + 新 API Key ⇒ 要重新生成 Key 并更新 `.env` 的 `DIFY_APP_KEYS`
2. ⚠️ **多轮上下文要显式接**：原 Chatbot 隐式带对话历史；Chatflow 的 LLM 节点必须手动把
   「对话历史」变量接进提示词，否则**丢多轮上下文** —— 这是最容易踩的一个
3. draft **必须 publish** 之后 API 才调得到
4. 旧应用不会自动删，要决定是否清理（否则 8 个变 12 个）
5. 好处：KB 从「隐式 dataset_config」变成显式 `knowledge-retrieval` 节点，
   **绕开了之前踩的 `dataset_configs...dataset.enabled=true` 那个坑**；但 top_k/score_threshold
   要改到节点里配置

### 建议路径（未执行，等用户决定）
先拿**一个**应用试点（建议「心理关怀 Agent」，业务最简单）：
转换 → 检查节点（重点看 LLM 节点有没有接对话历史）→ publish → 生成新 Key →
实测三件事（多轮对话是否保上下文、KB 引用是否还有、流式是否正常）。
验证 OK 再批量转剩下 3 个。

## 21:07 评估：能不能把 Dify 改成「单 Chatflow + 问题分类器扇出」这种模式

用户发来一张参考截图（Dify 里一个叫「学生端智能助手_ai」的 Chatflow，`用户输入 → 问题分类器(6类) → 各分支 → 整理结果(LLM) → 回复`，带 IF/ELSE 与回环），问「能做成这种模式吗」。

### 结论：能，而且比想象中近 —— 后端基础设施早就为此备好了

**关键发现：项目里已经有一条「给 Dify 反向调用」的内部接口。**

```
app/api/v1/router.py  →  internal_router（挂载在 /internal，与 /api/v1 分开）
app/api/v1/tools.py   →  GET  /internal/tools             工具清单（注释写明「给 Dify 配置 Tool 节点用」）
                         POST /internal/tools/{tool_name} 工具调用入口
app/services/agent_tools.py → 19 个 ToolSpec，每个带 min_role + JSON Schema
```

- 鉴权：`X-Tool-Timestamp` + `X-Tool-Signature` = `HMAC-SHA256(settings.tool_shared_secret, ts + "." + raw_body)`，
  再校验时间窗 ±300s；**没有旁路**（`verify_tool_signature` 里 signature 为空直接 False）。
- 工具级权限：`ctx.rank < spec.min_role` → `Forbidden`；调用方在 body 里带 `role`。
- 写工具两次调用：先 `{needs_confirm, preview, token}`，带 `confirm=<token>` 再调一次才落库。
- 覆盖度（TDD 声明 19 个）：`GET /internal/tools` 的 `coverage` 字段直接给。

### 当前架构（对比用）

- 路由在 **Python**：`app/services/intent.py` 的 `route()` =
  ① `PREFILTER_RULES` 关键词预筛（0 延迟）→ ② 未命中调 Dify `router` workflow →
  ③ `_apply_permission` 走 `ROLE_AGENTS` 矩阵（5 角色 × 6 agent）→ ④ 置信度分级 dispatch/clarify/fallback。

- 入口 `app/api/v1/chat.py` → `route()` → `dify_client.chat(agent)`。

### 真正的三个 gap（这是「难度大吗」的答案）

1. **签名**：`/internal/tools/*` 强制 HMAC，而 **Dify 自定义工具只支持 none/api_key/bearer，不会现算 HMAC**。
   ⇒ 建议给后端加一条「Dify 专用静态 Key（Bearer）」通道，仅在缺 HMAC 头时校验；HMAC 原路径不动。约 15 行 + 一条负向测试。
2. **权限**：`ROLE_AGENTS`（agent 级矩阵）在 Dify 里表达不了 —— 分类器不知道调用者是谁。
   但**工具级 `min_role` 后端还在管**，所以不会越权取数；需要重新定的是「visitor 该不该看到某个入口」。
3. **降级方向反过来**：现在是「连不上 Dify → 降级 mock + `degraded=True`」；
   Chatflow 里工具节点连不上后端只会走 fail-branch，对后端就是空 answer，**原可观测性在这个方向上看不见**，要另做。

另外两个必踩：转换（`convert-to-workflow`）是**新建应用** → 新 app_id + 新 Key，`.env` 的 `DIFY_APP_KEYS` 要改，
draft 必须 publish 后 API 才调得到；**Chatflow 的 LLM 节点必须显式接「对话历史」**，否则丢多轮上下文。
Dify 容器访问后端用 `host.docker.internal` = **192.168.65.254**。

### 根因（已抓包确认）

Dify 的 `conversation_id` **按应用隔离**。前端 `state.conversationId` 是全局的，
换类问题（客服 → 学员助手）时把上一个应用的会话递过去，Dify 回：

| 情况 | 响应 |
|---|---|
| 会话属于别的应用 | `404 {"code":"not_found","message":"Conversation Not Exists. ..."}` |
| id 是畸形值 | `400 {"errors":{"conversation_id":"... is not a valid uuid."}}` |

旧代码把这两类异常一并吞进「降级」分支 → 返回一段**与问题无关的 mock 套话**，
只在 UI 上留个 `degraded=true` 小标记。实测：带客服会话问成绩 = 套话；不带 = 真实成绩表。

### 修法（选择：**定向重试**，不改 API 契约）

理由：项目正在验收期，`conversation_id` 的形状写在需求/技术文档里，
不应该为了修 bug 去改对外契约。而且「换个应用本来就没有共同上下文」，
重开一次是语义正确的行为。

`app/services/dify.py`：
- 新增模块级 `_CONVERSATION_MISSING_HINTS = ("conversation not exists", "not a valid uuid")`

  / `_drop_conversation(payload)`；
- `chat()`：`client.post` 后先判 `_conversation_is_stale(resp)`，命中则
  **丢掉 conversation_id 递归重试一次**（只递归一层，因为重试时 conv=None）；
- `stream_chat()`：请求部分抽出 `_open_chat_stream()`，用 `contextlib.AsyncExitStack`
  持有 (client, resp)，命中陈旧会话时 `aclose()` 后**丢掉会话 ID 重开一次**再返回；
  返回 `(stack, resp, effective_conv)`，`finally: stack.aclose()` 保证连接释放。
  ⚠️ 流式下必须 `await resp.aread()` 才能读 body 判定；
  ⚠️ helper 内异常要自己 `aclose()` 再 raise，否则泄漏连接。
