### 需求
「让项目跑起来，并且生成一个一键启动脚本」

### 产出
| 文件 | 作用 |
|---|---|
| `ai-assistant/start.bat` | ★ 双击入口（纯 ASCII，负责找 python + 转发参数） |
| `ai-assistant/stop.bat` | 双击停止（转发 `start.bat --stop`，带 pause） |
| `ai-assistant/scripts/launcher.py` | 真正逻辑（约 600 行）：start / --stop / --status / --selfcheck / --headless / --smoke / --reseed |
| `ai-assistant/frontend/runtime-config.js` | 后端地址注入占位文件（新增） |
| `ai-assistant/tests/test_config.py` | 配置解析回归测试（新增 7 项） |
| `.run/` | 运行态：`pids.json` + `logs/`（已入 .gitignore） |

`start.bat` 的十步流程：找解释器 → 查依赖（缺了自动 pip 装）→ 无 `.env` 就复制 `.env.example`
→ 建库灌种子 → 挑空闲端口 → 起前后端（各开一个控制台窗口）→ 探活 → 落 PID → 打印横幅 → 开浏览器。

### 关键设计
- **端口自动避让**：探针校验业务特征（后端认 `code==0 && data.app`，前端认页面含"留学机构"），
  认出来是"自己人"就复用不起第二套；被外人占用就 +1 最多试 20 个。
- **端口变化自动通知前端**：`serve_frontend.py --api-base` 动态吐 `/runtime-config.js`，
  前端取值优先级 `localStorage` > `window.__UAS_API_BASE__` > `DEFAULT_API_BASE`。换端口不用改代码。
- **`--selfcheck`**：起服 → 13 项体检 → 收服，全程单进程。体检含登录换 JWT、
  无 token 访问 `/auth/me` 应 401、前端 index/main.js/styles.css 可加载、62 条冒烟测试。
- **`--headless`**：不开窗口，日志落 `.run/logs/`，给 CI / 无桌面环境用。

### 本轮修掉的真缺陷

**1. `.env` 里的 `CORS_ORIGINS` 让后端直接起不来（最严重）**

`.env.example` 里写的是逗号分隔：
```env
CORS_ORIGINS=http://127.0.0.1:8020,http://localhost:8020,...
```
但 pydantic-settings 对 `List` 这类复杂字段**默认要求 env 值是 JSON**，且在
**数据源层**（`DotEnvSettingsSource.decode_complex_value`）就先 `json.loads`，
**早于字段校验器**——所以 `field_validator(mode="before")` 完全救不了，直接抛
`SettingsError: error parsing value for field "cors_origins"`，uvicorn 一启动就崩。

**为什么之前 86 项测试全绿**：仓库里当时没有 `.env` 文件，测试只走代码内默认值，
这条路径压根没被执行。**一执行 launcher 生成 `.env` 就炸。**

修法（pydantic-settings 2.15）：字段标 `Annotated[List[str], NoDecode]` 关掉数据源层解码，
再自写 `field_validator(mode="before")` 同时接受逗号分隔与 JSON 数组。
回归测试 `tests/test_config.py` 锁住 4 件事：`.env.example` 可解析、键名无拼错、
CSV/JSON/空串/单值四种写法、无 `.env` 时的默认值。

**2. `start.bat` 里 `echo` 文案带括号 → cmd 解析崩溃**

`if not "!RC!"=="0" ( echo  ... (see messages above) ... )` 里的 `)` 被 cmd 当成
`if (...)` 块的结束符，提前闭合，然后报 `---- was unexpected at this time`，退出码 255。
**`.bat` 里 echo 文案禁止出现括号**。（同类：中文不能进 .bat，必须纯 ASCII。）

### ⚠️ 重要环境结论：沙箱会回收整棵进程树

做验证时发现「启动器报 pid 成功，但下一秒 PID 不存在、端口没监听、窗口里也没报错」。
做了对照实验（`_lab/tmp/launcher-verify/`）：用三种方式各起一个「写标记文件 + sleep 90s」的子进程，
父进程退出后由**另一次工具调用**检查：

| 派生方式 | 标记文件 |
|---|---|
| `DETACHED_PROCESS │ CREATE_NO_WINDOW` | 没写出来（被杀） |
| `CREATE_NEW_CONSOLE` + `cmd /k` | 没写出来（被杀） |
| `CREATE_NEW_CONSOLE │ CREATE_BREAKAWAY_FROM_JOB` | 没写出来（被杀） |

**结论：在本沙箱里，任何被派生的进程都会在工具调用结束时被回收。**
⇒ 验证必须塞进**单次工具调用**内（`--selfcheck` 就是为此设计的模式），
不能拆成「调用 A 起服 → 调用 B 验证」。
这不代表 console 模式有缺陷——真人双击 `start.bat` 不受此限制。

## 留学机构 AI 智能助手 —— 修复 mock 应答「数据类问题答不出 / 只会预设答案」

### 用户报的问题
截图里学员问「帮我查一下最近的意向客户跟进情况」，AI 回
「暂未查询到相关信息，建议咨询顾问获取准确答复」。但库里明明有跟进记录，
而且这条问题的路由结果就是 `enterprise_assistant / nl2sql_query`（置信度 0.92）。

### 根因（一句话）
mock 应答层**完全无视路由结果**：`dify._mock_chat_answer()` 只拿用户原话去撞一张
7 条目的静态关键词表，撞不上就回死胡同话术。受控 NL2SQL、角色范围、落库能力**早就有了**，
只是从来没被接到对话链路上。

### 修法：新增 `app/services/mock_agent.py`（按 intent 分派的本地编排层）
`chat.py` 在 mock 模式下改调 `mock_agent.respond(intent, message, role, db, subject=, ref_id=)`，
返回统一的 `DifyChatResult`（blocking 与 stream 两条路径都走它）。

| intent | mock 下的真实行为 |
|---|---|
| `nl2sql_query` | 真跑 `nl2sql.run_query()`；输出数据行 + 模板名 + SQL 预览；角色不够明说没权限 |
| `after_sales` | 真写 `after_sales_ticket`，10 分钟窗口内重复提交合并成一条 |
| `leave_apply` | 真写 `student_request`（`idempotency_key=chat-{subject}-{date}-{days}`）；槽位不全先追问 |
| 知识类 | `mock_kb_answer()` 检索语料（**最长关键词优先**）+ 标引用 |
| 兜底 | 讲清能力边界 + 列出可问问题 + 引导「转人工」 |

### 三个真缺陷
1. **`_pick_template` 按「命中个数」打分** →
   「帮我查一下最近的意向客户跟进情况」同时命中 `lead_status_stats`（客户+意向=2 个）和
   `lead_followups`（跟进情况=1 个），按个数排会错判成「状态分布」。
   改为 **最长关键词优先** `(max_len, count)`，`_mock_route`/`_match_kb` 同一套打分。
2. **`ROLE_AGENTS` 把 `customer_service` 只给了 visitor/admin** → 员工/学员问机构政策被降级。
   机构政策是公共信息，改成所有角色可达。
3. **语料里材料条目挂了裸「流程」关键词** → 「你们的服务流程是什么」被答成材料清单。
   拆出独立的「服务流程」条目（六步），材料条目只留「申请流程」这类具体组合。
   路由侧另加 5 字强信号词「各科平均分」：它和知识类「均分」只差一字，同分时靠前的知识规则会赢，
   于是「统计一下各科平均分」被答成均分要求。用长词压过，且**不误伤**「平均分要求是多少」的政策问法
   （已加回归用例锁住）。

### 附带补的
- `nl2sql.TEMPLATES` 新增聚合模板 `score_averages`（各科平均分，`GROUP BY subject` + `AVG`）。
- 工单答复按角色说话：`/api/v1/tickets` 是 `staff_only`，学员侧只有提交入口，
  所以不再对学员承诺「去学员中心工单页看进度」。
- **`launcher.py --stop` 加了按端口兜底清理**：PID 记录会失效（控制台窗口被关/进程被回收），
  老的 `--stop` 会报「可能已经退出」但服务还在跑、端口一直被占。
  现在除按 PID 外，还按端口用**探针确认是自己人**再结束占用进程（不误伤同端口的其他程序）。

### B. 「你好」掉进兜底话术

截图：admin 输入「你好」，回的是「这个问题我暂时没有可用的信息，不能凭空给你答复。」
—— 开场体验灾难。根因：**寒暄类输入没有任何处理**，路由给 `customer_service/unknown`
（置信度 0.4）后直接落到 `MOCK_NO_RECALL_TEXT`。

修法：`mock_agent._handle_smalltalk()`，放在 `respond()` **最前面**，覆盖
问候 / 感谢 / 应答词 / 告别 / 能力询问。

⚠️ **判定必须严格**：只有「把开头的寒暄词和标点逐个吃掉后整句已空」才算寒暄
（`_consume_tokens` + `_is_only`，长词优先以免「早上好」被「早」截断）。
否则「你好，请问雅思要考多少分」会被寒暄吞掉 —— 从「答非所问」恶化成「干脆不答」。

### B2. 寒暄修复踩出的第二个缺陷：礼貌前缀污染查询参数

修完寒暄后复测组合句，发现「好的，帮我查一下最近的意向客户跟进情况」**查出 0 条**，
而「帮我查一下最近的意向客户跟进情况」（无前缀）查 7 条。

根因：路由正确（`nl2sql_query`），但 `_extract_param` 把句首的「好的」（2 个纯中文）
当成了客户姓名 → `WHERE l.name LIKE '%好的%'` → 空集。

修法：`_strip_leading_pleasantry()` —— 在 `leave_apply` / `nl2sql_query` 两条分派前，
先用 `_consume_tokens` 剥掉句首寒暄词（长词优先）再交给槽位抽取。
回归用例断言「带礼貌前缀」与「不带前缀」**返回相同行数**。

⚠️ 教训：**寒暄识别与槽位抽取必须共用同一套 token 表且顺序一致**，
否则「识别出是寒暄」和「抽取时不带寒暄」会各说各话。

## 留学机构 AI 智能助手 —— 双击 start.bat 弹窗报「不是内部或外部命令」

### 用户报的现象
截图：标题为「AI Assistant - Frontend」的控制台窗口，里面两行：
```
'"C:\Users\机械革命\.workbuddy\binaries\python\envs\default\Scripts\python.exe"' 不是内部或外部命令，也不是可运行的程序或批处理文件。
C:\Users\机械革命\WorkBuddy\2026-09-12-11-04-16\ai-assistant>
```
注意 `title AI Assistant - Frontend` **执行成功了**（窗口标题设上了），
失败的是 `&&` 后面那句 —— 说明是**引号解析**问题，不是路径不存在。

### 根因（已被实测钉死）
`launcher.py::spawn_console` 原本这么写：
```python
inner   = " ".join([f'"{py}"'] + [f'"{a}"' if " " in a else a for a in args])
cmdline = f'title {title} && {inner}'
subprocess.Popen(["cmd", "/k", cmdline], creationflags=CREATE_NEW_CONSOLE)   # ← 传的是 list
```
传 **list** 时 Python 会先用 `subprocess.list2cmdline` 拼命令行，它把 `cmdline`
整体包上引号、并把**内层引号转义成 `\"`**：
```
cmd /k "title AI Assistant - Frontend && \"C:\...\python.exe\" ..."
```
而 **cmd.exe 不认反斜杠转义** —— 它于是去找一个字面名叫
`\"C:\...\python.exe\"` 的文件，报「不是内部或外部命令」。
**报错里那个 `\"` 就是铁证**（用户截图低分辨率看着像纯引号）。

### 修法
新增 `console_cmdline(title, py, args) -> str`，返回**一整行原始命令行**，
调用方必须把它当**字符串**传给 `Popen`（字符串 = 原样交 CreateProcess，不再二次转义）：
```python
raw = f'cmd /k "title {title} & "{py}" {arg}"'
subprocess.Popen(raw, creationflags=CREATE_NEW_CONSOLE)
```
cmd 的规则：引号数 > 2 时掐掉最外层首尾两个引号 → 得到可正常解析的
`title X & "C:\...\python.exe" args`。另加 `_cmd_quote_arg()`：
含空格或 cmd 元字符（`&()[]{}^=;!'+,`~`）的参数自己包引号。

**另一个顺手修掉的隐患**：分隔符用 `&` 而**不是** `&&`。`title` 只是改窗口标题的
装饰动作，用 `&&` 时它一旦失败，后面的服务**根本不会启动** —— 把「装饰失败」
放大成「服务起不来」。`&` 是无条件继续。

## WorkBuddy 侧边栏「会话一直转圈」—— 定位与修复

### 现象
用户截图：侧边栏一条深色胶囊，粗体「再次尝试操作」+ 右侧转圈，问「为什么还在转」。

### 排查路径（可复用的方法）
1. **先证伪「是不是我的后台进程」**：`Get-CimInstance Win32_Process` 过滤
   `python/uvicorn/serve_frontend` + `netstat -ano | LISTENING` → 全空。
2. **再找文案来源**：把 `Programs\WorkBuddy\resources` 整个目录按字节搜
   （`app.asar` 284MB + `locales\zh-CN.pak`）。结论：`再次尝试操作` **不在**应用内，
   只在 `~/.workbuddy/traces/**` 命中 → 那是**模型生成的文本**（自动会话标题），
   不是 UI 内置文案。trace 里能看到模型返回 `{"isNewTopic":true,"title":"再次尝试操作"}`。
3. **再读应用自己的状态**（**只读**，`file:...?mode=ro`）：
   - `~/.workbuddy/sessions/<pid>.json`：`{pid, sessionId, cwd, lastHeartbeat, url}` ——
     这就是「traces/<pid> ↔ sessions.id」的对应表。心跳在跳 ⇒ 那个会话就在跑。
   - `workbuddy.db` 的 `sessions` 表：`status` 取值 Pending / working / completed /
     archived / error。**转圈 = status 为 `working`。**
   - 结论：那条「再次尝试操作」= `3ea2718f…` = **当前这场对话自己**（cwd 一致、
     `last_activity_at` 正好等于用户发消息那一刻、心跳实时更新）。所以它转是正常的。
4. **才找到真正的这两个**（`status='working'` 共 3 个，除当前会话外 2 个是死的）：
   | id | title | 最后活动 |
   |---|---|---|
   | `a86dcc48…` | 股市复盘 | 09-10 16:07（bg=1 后台自动化会话） |
   | `4eeca02a…` | 查看后台命令 cloud_exp 执行结果 | 09-12 11:48 |
5. **确认它们确实没在跑**：`automation_runtime_state.running=0`；
   进程表里**没有**对应的 `WorkBuddy.exe … codebuddy --prewarm` 子进程；
   `sessions/<pid>.json` 不存在。

### 根因
**09-10 16:09:53/56 用户把两个自动化删掉了**（`automations` 表软删，
`deleted_at` 有值；两张表 `status` 仍留 `ACTIVE`），
但**那两个自动化对应的后台会话的 `sessions.status` 没被一起收尾**，
永久停在 `working`。应用启动时**没有** reconcile 逻辑，所以这两个转圈
熬过了 09-10 之后的多轮重启（09-14 09:30 这次启动也没修）。
⇒ 纯粹是**状态标记不准**，不占资源、不影响功能；`automation_runtime_state.running=0`
说明自动化本身早就停了。

### 修复（已执行，用户确认后）
```python
# 1) 一致性快照（用 SQLite backup API，应用在写也安全）
src = sqlite3.connect(db); dst = sqlite3.connect(bak); src.backup(dst)
# 2) 只改 status 一列；带 status='working' 兜底，避免误改正在跑的会话
UPDATE sessions SET status='completed'
 WHERE id IN ('a86dcc48…','4eeca02a…') AND status='working'
```
- 备份：`C:\Users\Public\wb_backup\workbuddy.db.20260914-120753.bak`（352256 B）
- 结果：`affected rows = 2`；两行变 `completed`；**`updated_at` 保持原样**
  （不把老会话顶到列表最前）；`automations` 表前后都是 2 行 2 软删 —— **未触碰**。
- 复检：`status='working'` 只剩 `3ea2718f`（当前对话）。

### 边界（重要）
- `automations` / `automation_runtime_state` 等表**绝不**用 sqlite 或脚本改，
  只能走应用 UI 或 `automation_update` 工具。（本次只改了 `sessions.status`。）
- 应用正在运行、持有该 db：改动可能被内存缓存挡住，**UI 不刷新就切一下会话或重启应用**。
